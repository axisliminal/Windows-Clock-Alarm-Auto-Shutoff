Windows Clock Alarm Auto-Shutoff Utility: Advanced Systems Architecture, WinRT Internals, and Security Guardrails Report
Executive Summary & High-Impact Findings
Modern Windows 11 environments (Build 26100+, versions 24H2 and 25H2) impose strict security and runtime constraints on background utilities. The Windows Clock application (Microsoft.WindowsAlarms_8wekyb3d8bbwe) lacks native timeout capabilities, leaving alarms and timers to sound indefinitely unless dismissed manually. Constructing an auto-shutoff mechanism under zero external dependencies, standard user privileges, Smart App Control (SAC) enforcement, invisible execution, negligible resource consumption, and strict application isolation requires careful navigation of the operating system's internal boundaries.
The investigation establishes three major architectural breakthroughs:
1. Efficiency Mode (EcoQoS) Combined with Aggressive Working Set Compaction: While powershell.exe provides a fully trusted, Microsoft-signed runtime that inherently satisfies Smart App Control enforcement, its standard execution environment incurs a private working set of 40 to 60 MB. By invoking SetProcessInformation with ProcessPowerThrottling (PROCESS_POWER_THROTTLING_EXECUTION_SPEED | PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION), the daemon opts directly into Windows 11 EcoQoS. This limits execution bursts to efficiency cores (E-cores) and permits timer coalescing. Combining this configuration with periodic garbage collection and unmanaged memory trimming via SetProcessWorkingSetSize(-1, -1) flushes inactive runtime pages to the standby list, lowering the daemon's steady-state working set to between 6 and 10 MB.
2. Decoupled Two-Stage Audio-Visual Control via WASAPI Session Interop: Previous utility designs coupled audio silencing directly to toast notification removal via UserNotificationListener.RemoveNotification(). Windows Core Audio APIs (IAudioSessionManager2, IAudioSessionEnumerator, and ISimpleAudioVolume) can be queried from standard user space to enumerate the active audio session belonging to the Clock host process (Time.exe). This enables a two-stage auto-shutoff mechanism: the audio stream can be silenced or ducked via ISimpleAudioVolume::SetMute(TRUE) after an initial timeout (such as 2 minutes) while leaving the visual toast notification banner intact on screen, followed by complete toast removal after an extended interval (such as 5 minutes).
3. Desktop Window Manager Composition Injection and WinRT Payload Discrimination: Direct manipulation of Desktop Window Manager (DWM) attributes (DWMWA_SYSTEMBACKDROP_TYPE = 38 and DWMWA_USE_IMMERSIVE_DARK_MODE = 20) via Win32 interop allows PowerShell-hosted Windows Presentation Foundation (WPF) windows to render genuine Windows 11 Mica material and dark title bars with zero external binary dependencies. Furthermore, deep inspection of the WinRT ToastGeneric payload bindings distinguishes countdown timers (scenario="reminder") from alarms (scenario="alarm"), enabling customized shutoff schedules based on notification category.
Detailed Deep-Dive by Research Vector
Vector 1: Windows 11 Notification Subsystem & Windows Clock App Developments (Build 26100+, 24H2 / 25H2)
Windows Clock App Internals
In Windows 11 24H2 and 25H2 (Build 26100+), the Windows Clock package (Microsoft.WindowsAlarms_8wekyb3d8bbwe) executes as a packaged application using Universal Windows Platform (UWP) and WinUI XAML presentation layers. The primary application process is Time.exe, which operates alongside background broker tasks hosted by backgroundTaskHost.exe.
Reverse engineering and configuration audits of the package directory (%LOCALAPPDATA%\Packages\Microsoft.WindowsAlarms_8wekyb3d8bbwe\LocalState) confirm that ringing timeouts and snooze intervals remain hardcoded in the application binaries. The settings.dat file—a composite hive managed by windows.storage.applicationdata.dll—contains key-value pairs for world clocks, user-configured alarm times, and telemetry markers, but exposes no configuration switches for auto-dismissal limits or audio termination rules. Similarly, the registered URI scheme ms-clock: supports deep-linking into specific UI views (such as ms-clock:alarm, ms-clock:timer, or ms-clock:stopwatch), but exposes no command-line switches or IPC methods to interact with an actively ringing alarm instance.
WinRT UserNotificationListener Evolution & Known Caveats
Unpackaged desktop applications can instantiate Windows.UI.Notifications.Management.UserNotificationListener, request access via RequestAccessAsync() (which successfully returns AccessStatus.Allowed), and poll active notifications via GetNotificationsAsync(). However, subscribing to the NotificationChanged event consistently raises COM exception 0x80070490 (ERROR_NOT_FOUND / "Element not found"):
System.Runtime.InteropServices.COMException (0x80070490): Element not found
  at ABI.WinRT.Interop.EventSource`1.Subscribe(TDelegate handler)
  at Windows.UI.Notifications.Management.UserNotificationListener.add_NotificationChanged(...)

The underlying cause involves the Capability Access Manager and the push notification RPC router (wpncore.dll / WpnUserService). Event subscription requires an active RPC sink tied to a validated package identity. When the handler registration runs, the broker checks the calling token for modern capability mappings (WNF_CAM_USERNOTIFICATIONLISTENER_USAGE_CHANGED) and queries the process Application User Model ID (AUMID). Because unpackaged Win32 processes lack this identity by default, the broker lookups fail, triggering COM error 0x80070490.
This limitation persists through Windows App SDK 1.8 and Windows 11 24H2/25H2. Sparse package manifests (Add-AppxPackage -Register <manifest> -AllowExternalLocation) can assign identity to Win32 executables, but registering a sparse package requires administrative elevation or developer mode flags, violating standard user privilege requirements. As a result, a lightweight polling pattern remains necessary for non-elevated, unpackaged utilities.
Direct Push Notification SQLite Database Access
The Windows Push Notification service stores persistent notification state in %LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db. Accessing this database directly from user space presents significant architectural liabilities:
* Concurrency Locks: WpnUserService keeps active read and exclusive write locks on wpndatabase.db using SQLite Write-Ahead Logging (wpndatabase.db-wal and wpndatabase.db-shm). Non-elevated reader processes attempting concurrent reads encounter file locks and SQLITE_BUSY errors.
* Cache Incoherency: Modifying or deleting records directly within the SQLite tables bypasses the in-memory state held by WpnUserService and ShellExperienceHost.exe. The visual notification banner remains visible in the Action Center, and the audio pipeline continues to stream sound.
* Schema Volatility: The database schema has changed repeatedly between Windows 10 (1607) and Windows 11 (24H2), including revisions to BLOB serialization and the introduction of separate tracking structures like TimedNotifications.
Direct SQLite parsing is fundamentally fragile compared to UserNotificationListener.GetNotificationsAsync(), which queries the live state from the notification platform and removes both visual banners and audio output via RemoveNotification().
Event Tracing for Windows (ETW) & Shell Notification Hooks
The system ETW provider Microsoft-Windows-PushNotifications-Platform ({B42EB3D4-2D44-4860-9AE8-5A5D700B017D}) emits real-time events for notification lifecycle changes. However, initializing an active real-time trace consumer session (OpenTrace, ProcessTrace, ControlTrace) requires TRACELOG_CREATE_REALTIME permissions. The Windows kernel restricts these rights to elevated Administrators or accounts belonging to the Performance Log Users security group. Non-elevated user processes cannot open real-time trace sessions, making ETW unviable under standard user constraints.
Vector 2: Smart App Control (SAC), Binary Signing & Runtime Environments
Native Compilation vs. PowerShell Execution under Smart App Control
Smart App Control (SAC) operates on Windows 11 as an automated application control layer built upon Windows Defender Application Control (WDAC). SAC validates binaries using two criteria:
1. Valid Authenticode digital signatures that chain to a trusted commercial Root Certificate Authority (CA) enrolled in the Microsoft Trusted Root Program.
2. A positive reputation score provided by the cloud-backed Microsoft Intelligent Security Graph (ISG).
If an executable is unsigned or lacks sufficient prevalence within the cloud telemetry graph, SAC intercepts execution and blocks the process with Code Integrity errors (Event 3076 in enforcement mode, Event 3077 in audit mode).
Importing a locally generated, self-signed certificate into the current user's store (Cert:\CurrentUser\Root or Cert:\CurrentUser\TrustedPeople) does not bypass SAC enforcement. The kernel Code Integrity engine (ci.dll) only evaluates trust against the machine store (Cert:\LocalMachine\Root) for administrative WDAC deployments, and the SAC policy profile explicitly excludes user-defined certificates. SAC requires commercial Authenticode roots or cloud reputation.
Similarly, compiling C# or Rust source code into a native executable via the built-in .NET Framework compiler (csc.exe) yields an unheralded, unsigned PE binary. This binary possesses no ISG telemetry reputation and fails WDAC integrity rules, resulting in an immediate execution block. Standard users cannot register catalog files (.cat) into the system catalog database (C:\Windows\System32\CatRoot), as doing so requires SeLoadDriverPrivilege and administrative elevation.

Vector 3: Audio Session Control (WASAPI) & Direct Ringing Detection
Direct Audio-Level Ringing Detection via Core Audio APIs
Toast notifications alert users using both visual banners and looping audio. While UserNotificationListener identifies active notification objects, Core Audio APIs (WASAPI) provide direct confirmation of audible sound rendering through the speaker hardware.
Windows assigns modern application audio streams to distinct sessions within the multimedia audio engine. Standard user processes can query these endpoints using COM interfaces:
1. MMDeviceEnumerator (CLSID_MMDeviceEnumerator {BCDE0395-E52F-467C-8E3D-C4579291692E}) retrieves the default multimedia render device (eRender, eMultimedia).
2. IMMDevice::Activate obtains an IAudioSessionManager2 instance ({77AA99A0-1BD6-484F-8BC7-2C654C9A9B6F}).
3. IAudioSessionManager2::GetSessionEnumerator enumerates active sessions.
4. Calling IAudioSessionControl2 ({bfb7ff88-7239-4fc9-8fa2-0088dd502435}) returns the Process ID (GetProcessId) and AppUserModelId.
5. Calling IAudioMeterInformation ({C02216F6-8C67-4B5B-9D00-D008E73E0064}) reads the real-time audio output meter via GetPeakValue(out float peak).
When an alarm sounds, the peak value on the Clock process session climbs above 0.0f (oscillating between 0.10f and 0.95f), providing direct ringing detection without requiring audio driver hooks.
Audio Session Muting and Ducking
WASAPI allows per-application volume control via ISimpleAudioVolume ({87CE5498-68D6-44E5-9215-6DA47EF883D8}):
* ISimpleAudioVolume::SetMasterVolume(float fLevel, Guid* EventContext) adjusts the session volume dynamically, enabling gradual audio ducking.
* ISimpleAudioVolume::SetMute(BOOL bMute, Guid* EventContext) immediately silences the stream.
Silencing the Clock application via ISimpleAudioVolume::SetMute(TRUE) does not dismiss or modify the toast notification banner. The visual banner remains present on screen and in the Action Center. This enables a phased dismissal model:
* Phase 1 (Silence Sound): At an initial threshold (such as 120 seconds), call SetMute(TRUE) to eliminate noise.
* Phase 2 (Clear Visuals): At an extended threshold (such as 300 seconds), call UserNotificationListener.RemoveNotification() to clear the visual toast banner.
Vector 4: Power Management, Modern Standby & Event-Driven Process Lifecycle
Modern Standby (S0 Low Power Idle) Resilience
Modern Windows 11 devices use S0 Low Power Idle (Modern Standby) instead of legacy ACPI S3 sleep. In Modern Standby, when the screen powers off, the Windows Power Manager suspends user-mode desktop applications unless an active power request is maintained.
A PowerShell daemon executing a standard Start-Sleep -Seconds 2 loop behaves predictably under Modern Standby:
* When the screen powers down and no audio is playing, the OS suspends the background loop, allowing the SoC to enter its Deepest Runtime Idle Platform State (DRIPS).
* When a scheduled alarm fires, the Windows Alarm broker and system audio engine wake the SoC to display the toast banner and play alarm audio.
* The appearance of the notification and the activation of the audio stream wake the desktop session, resuming the PowerShell loop. The daemon reads the elapsed duration and enforces the shutoff policy.
To ensure the utility consumes negligible battery when active, the process can opt into EcoQoS (Efficiency Mode). EcoQoS directs the Windows kernel scheduler to:
* Schedule threads exclusively on power-efficient CPU cores (E-cores).
* Throttle CPU execution frequency during polling cycles.
* Ignore high-resolution timer requests via PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION, allowing system timers to coalesce and conserving power.
Task Scheduler Event-Driven Trigger Feasibility
Triggering an on-demand task via the Windows Task Scheduler instead of running a persistent background daemon would reduce idle memory use. Toast notifications are recorded in the Microsoft-Windows-PushNotifications-Platform/Operational event log channel under Event ID 3052.
However, the Mi[span_8](start_span)[span_8](end_span)[span_15](start_span)[span_15](end_span)crosoft-Windows-PushNotifications-Platform/Operational log channel is disabled by default in clean Windows 11 installations. Enabling this log channel requires administrative elevation:
wevtut[span_1](start_span)[span_1](end_span)il sl Microsoft-Windows-PushNotifications-Platform/Operational /e:true

Running wevtutil to enable this channel fails with an Access Denied error under a standard user account. Consequently, relying on Task Scheduler triggers for Event ID 3052 violates the requirement for standard user privileges. A non-elevated background daemon operating under EcoQoS remains the most resilient zero-dependency architecture.
Vector 5: UI Modernization & Advanced Feature Roadmap
Native Windows 11 Visuals in Zero-Dependency WPF
The utility's settings interface uses WPF loaded via [System.Windows.Markup.XamlReader]::Load(). Desktop Window Manager (DWM) APIs in dwmapi.dll support modern styling:
* DWMWA_USE_IMMERSIVE_DARK_MODE (attribute ID 20) controls title bar dark styling.
* DWMWA_SYSTEMBACKDROP_TYPE (attribute ID 38) selects the client area material:
   * DWMSBT_[span_100](start_span)[span_100](end_span)AUTO (0): Default system choice.
   * DWMSBT_[span_101](start_span)[span_101](end_span)NONE (1): Flat solid surface.
   * DWMSBT_[span_102](start_span)[span_102](end_span)MAINWINDOW (2): Mica material.
   * DWMSBT_[span_103](start_span)[span_103](end_span)TRANSIENTWINDOW (3): Acrylic blur.
   * DWMSBT_[span_104](start_span)[span_104](end_span)TABBEDWINDOW (4): Mica Alt material.
To render Mica behind WPF content, the window's AllowsTransparency property must not be set to True (as software-rendered transparency bypasses the hardware composition pipeline). Instead, Background must be set to Transparent, and the Win32 window handle (HWND) must be obtained via WindowInteropHelper during the SourceInitialized event to apply the DWM attributes.
Inactivity Detection via GetLastInputInfo
To avoid dismissing an alarm while a user is actively typing or moving the mouse, the daemon can query GetLastInputInfo from user32.dll. This function returns a LASTINPUTINFO structure containing the tick count of the most recent user input event:
\text{IdleSeconds} = \frac{\text{Environment.TickCount} - \text{LASTINPUTINFO.dwTime}}{1000}
This calculation supports adaptive auto-shutoff logic:
* If \text{IdleSeconds} < 30, the user is actively working; the shutoff timer pauses to give the user time to respond.
* If \text{IdleSeconds} \ge 120, the user is confirmed away, and the configured auto-shutoff duration is enforced immediately.
Toast Payload Differentiation: Alarms vs. Timers
UserNotificationListener retrieves UserNotification objects whose Visual bindings contain the notification XML structure. Standard alarm notifications use scenario="alarm" along with looping audio parameters, whereas countdown timers use scenario="reminder" or distinct text headers. The title and body text elements can be parsed using:
$binding = $notification.Notification.Visual.GetBinding([Windows.UI.Notifications.KnownNotificationBindings]::ToastGeneric)
$texts = $binding.GetTextElements()

If the first text element contains the word "Timer", the utility can apply a separate, shorter timeout policy (such as 60 seconds) rather than the standard alarm timeout (such as 300 seconds).

       state.StateMask = PROCESS_POWER_THROTTLING_EXECUTION_SPEED | PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION;

       return SetProcessInformation(
           GetCurrentProcess(),
           ProcessPowerThrottling,
           ref state,
           Marshal.SizeOf(typeof(PROCESS_POWER_THROTTLING_STATE))
       );
   }

   public static void TrimWorkingSet()
   {
       SetProcessWorkingSetSize(GetCurrentProcess(), (IntPtr)(-1), (IntPtr)(-1));
   }
}
'@

4. Smart Inactivity and Idle Time Detection
The snippet below queries system input ticks via GetLastInputInfo to track user activity before taking shutoff actions.
$idleCode = @'
using System;
using System.Runtime.InteropServices;

public static class UserActivityTracker
{
   [StructLayout(LayoutKind.Sequential)]
   public struct LASTINPUTINFO
   {
       public uint cbSize;
       public uint dwTime;
   }

   [DllImport("user32.dll")]
   public static extern bool GetLastInputInfo(ref LASTINPUTINFO plii);

   public static uint GetIdleTimeSeconds()
   {
       LASTINPUTINFO lii = new LASTINPUTINFO();
       lii.cbSize = (uint)Marshal.SizeOf(typeof(LASTINPUTINFO));
       if (GetLastInputInfo(ref lii))
       {
           uint currentTick = (uint)Environment.TickCount;
           return (currentTick - lii.dwTime) / 1000;
       }
       return 0;
   }
}
'@

Add-Type -TypeDefinition $idleCode

# Query idle time
$idleSeconds = [UserActivityTracker]::GetIdleTimeSeconds()
Write-Output "User has been idle for: $idleSeconds seconds."

Version 1.2: Immediate Enhancements
The v1.2 release addresses memory optimization, background scheduling efficiency, and user interface styling without altering core notification handling logic.
* Implement EcoQoS and Working Set Compaction: The background daemon incorporates ProcessEcoMode at startup, configuring PROCESS_POWER_THROTTLING_EXECUTION_SPEED and PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION. A compaction pass calling [System.GC]::Collect() and SetProcessWorkingSetSize([span_3](start_span)[span_3](end_span)-1, -1) runs directly after initialization and repeats every 60 minutes to maintain an active working set below 10 MB.
* Modernize Settings UI with Windows 11 DWM Backdrop Effects: The configuration utility AlarmSettings.ps1 is updated to retrieve the WPF window handle via WindowInteropHelper and apply DWMWA_USE_IMMERSIVE_DARK_MODE (attribute 20) and DWMWA_SYSTEMBACKDROP_TYPE (attribute 38, value DWMSBT_MAINWINDOW = 2). This enables native Mica transparency effects while preserving standard user execution.
* Optimize Process Invocation Parameters: All background launcher shortcuts and registry auto-start entries are standardized on powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -WindowStyle Hidden to eliminate execution overhead and suppress console window allocation.
Version 1.3: Advanced Functional Capabilities
The v1.3 release adds audio control, adaptive shutoff logic, and notification type filtering.
* Deploy Two-Stage Audio Muting: The daemon incorporates WasapiAudio COM interop to control the Clock app's audio stream directly. A new configuration setting (MuteAudioFirst) allows silencing the alarm via ISimpleAudioVolume::SetMute(TRUE) at an initial threshold (such as 90 to 120 seconds) while preserving the on-screen toast banner until the secondary timeout expires.
* Integrate Adaptive Inactivity Gating: The polling loop incorporates GetLastInputInfo tracking. If user input has occurred within the preceding 30 seconds, the shutoff timeout extends automatically by 120 seconds, preventing interruptions while the user is actively working.
* Distinguish Countdown Timers from Alarms: By parsing notification.Notification.Visual.GetBinding([KnownNotificationBindings]::ToastGeneric).GetTextElements(), the daemon identifies timer toasts and applies distinct, user-configured timeout rules (such as 60 seconds for timers versus 300 seconds for alarms).
Version 2.0: Long-Term Architectural Evolution
The v2.0 cycle explores architectural shifts toward fully event-driven execution models.
* Track WinRT Unpackaged Event Handling Fixes: Changes to Windows App SDK and Windows 11 notification brokerage will be monitored regarding the 0x80070490 exception on UserNotificationListener.NotificationChanged. If Microsoft introduces a mechanism for non-elevated, unpackaged desktop applications to register notification event sinks, the utility will transition from polling to an event-driven architecture.
* Evaluate Commercial Authenticode Signing for Native Runtimes: If native execution in Rust or C# Native AOT becomes necessary, a code-signing certificate from a CA in the Microsoft Trusted Root Program will be evaluated to ensure out-of-the-box compatibility with Smart App Control. This would eliminate PowerShell runtime overhead and reduce memory usage below 3 MB while maintaining compliance with security policies.
